# Torrid Phase 5 (Add any temperature sensor) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Let the user add any temperature sensor LibreHardwareMonitor can see — motherboard/VRM/chipset, extra CPU sensors (CCDs, SoC…), storage, memory, extra GPU sensors — from an **Add sensor** button on the Sensors page, and show/alert/tray them exactly like the built-in four. Also make the built-in CPU sensor work on Intel (today it only matches AMD's sensor name).

**User request (verbatim):** "shouldnt there be a button to add sensors, for base its okay but for example if someone wants motherboard vrms, or cpu hotspot"

**Architecture:** `Torrid.Core` gets (a) new `SensorKind` values and generic sensor ids of the form `hw:<LibreHardwareMonitor sensor identifier>`, (b) `AppConfig.AddedSensors` remembering what the user added (so an added sensor still has a row, a name and its hardware group when it is not currently readable), (c) a snapshot/builder that finds added sensors anywhere in the hardware tree by identifier, (d) a **driver-footprint-minimising** `SensorService`: it only opens the hardware groups it needs (CPU always at Full level as before; Motherboard / Memory only when the user added a sensor of that kind and the anti-cheat level is Full; Storage when needed and level is Full or GpuOnly; GPU always) and offers an explicit, user-triggered `Scan()` that lists every temperature sensor. `Torrid.App` adds the **Add sensor** panel to the Sensors page.

**Tech Stack:** C#/.NET 8, WPF, LibreHardwareMonitorLib 0.9.6, xunit. Same solution as before.

- Anti-cheat contract is unchanged and must stay true: policy is evaluated BEFORE any hardware is opened; Paused opens nothing; GpuOnly never enables any group that uses the PawnIO driver (CPU, Motherboard, Memory — they use PawnIO for MSR/LPC/SMBus access); Storage uses plain user-mode IOCTLs, so it is allowed at GpuOnly. `Scan()` must refuse (return an empty result and a reason) while Paused, and under GpuOnly only scan GPU + Storage.
- Sensor ids: existing ids (`cpu`, `gpu{N}-core|hotspot|vram`) are unchanged and stay valid. New generic ids are `hw:` + LibreHardwareMonitor's `ISensor.Identifier.ToString()` (e.g. `hw:/amdcpu/0/temperature/3`, `hw:/lpc/nct6798d/0/temperature/4`, `hw:/nvme/0/temperature/0`). The part after `hw:` must be non-empty, contain no whitespace/control characters and be at most 200 chars; anything else is not a valid id.
- New `SensorKind` values (append after `GpuVram`, do not reorder the existing ones; the enum is serialized as dictionary keys in config so existing names must not change): `CpuOther`, `GpuOther`, `Motherboard`, `Storage`, `Memory`, `OtherTemp`. Default thresholds (blue < / green < / yellow <=, red above): CpuOther 40/70/85, GpuOther 50/85/95, Motherboard 45/70/90, Storage 40/55/70, Memory 40/60/80, OtherTemp 45/70/85. Titles on the Thresholds page: "Other CPU sensors", "Other GPU sensors", "Motherboard / VRM", "Storage", "Memory", "Other sensors".
- Defaults for a sensor the user adds: show in window ON, show in tray OFF, alerts ON (stored as explicit overrides when they differ from the per-kind default; `SensorDefaults` for the new kinds is: window false, tray false, notify true — the add action writes the explicit window=true override).
- Threshold colouring semantics, tray behaviour (one icon per tray-enabled sensor), settings live-apply, and everything from Phases 1-4 stay as they are. All existing tests must keep passing.
- Keep the per-poll cost low: no per-tick allocations beyond what exists; added-sensor lookup uses a dictionary built once per structure change, not per tick, where practical.

## Review Focus

1. Anti-cheat footprint: with no added motherboard/memory sensors, the set of enabled LibreHardwareMonitor groups is identical to today (CPU+GPU at Full, GPU at GpuOnly, none when Paused); a Motherboard/Memory group is NEVER enabled at GpuOnly or Paused; `Scan()` can't open drivers while Paused.
2. An added sensor that is not currently readable (hardware gone, group not enabled, access level reduced) still has a row/name/kind from `AddedSensors` and a `null` reading — never a crash, never a stale value, never an alert.
3. Ids are validated: hand-edited garbage in `AddedSensors`/`Sensors` keys is ignored without crashing; duplicate identifiers across hardware don't produce duplicate rows.
4. Group set changes (user adds the first motherboard sensor / removes the last one) reopen the `Computer` exactly once, without leaking a `Computer` and without blocking the UI thread.
5. The Add sensor UI never freezes the window: `Scan()` runs off the UI thread (Task.Run) and its result is marshalled back.

**Interfaces (later tasks rely on these exact names):**
- `SensorKind` gains `CpuOther, GpuOther, Motherboard, Storage, Memory, OtherTemp`.
- `SensorIdentity.TryParse("hw:/x/y")` returns `new SensorIdentity("hw:/x/y", defaultLabel: <identifier tail, e.g. "/x/y">, Kind: SensorKind.OtherTemp, GpuIndex: null)`. - `sealed class AddedSensor { string Name; string? HardwareName; SensorKind Kind; }` (public settable props so System.Text.Json round-trips them; `Kind` serialised as a string via `JsonStringEnumConverter`).
- `AppConfig.AddedSensors : Dictionary<string, AddedSensor>` (default empty; `JsonConfigStore.Normalize` drops null entries, entries whose key is not a valid `hw:` id, and entries with a blank `Name`; never throws).
- `SensorDisplay` overloads that take a `SensorReading` already work through `reading.Kind`; add `SensorDisplay.Identity(AppConfig, string id)` returning `SensorIdentity?`: for a built-in id → `SensorIdentity.TryParse`; for an `hw:` id that has an `AddedSensors` entry → `ForAdded`; otherwise `null`.
- `HardwareSnapshot` and `SensorSnapshot` gain a trailing `string? Identifier = null` parameter (default null so existing positional constructions still compile): hardware identifier and sensor identifier strings.
- `SensorReadingBuilder.Build(IReadOnlyList<HardwareSnapshot> hardware, IReadOnlyCollection<string>? addedSensorIds = null, Func<string, AddedSensor?>? addedInfo = null)`: unchanged output for the built-ins, PLUS one reading per id in `addedSensorIds`, found by `SensorSnapshot.Identifier` anywhere in the tree (recurse through `SubHardware`; first match wins), with `Id = id`, `Label = info?.Name ?? sensor.Name`, `Kind = info?.Kind ?? KindFor(hardwareType)`, `GpuIndex = null`, `ValueCelsius = sensor.Value` (null if the sensor is not Temperature type or not found), `HardwareName`, `SourceSensorName`. An added id that is not found yields a reading with `ValueCelsius = null` (so the row/card shows "--") using `info` for label/kind (skip it entirely only if there is neither a match nor `info`).
- Static helper `SensorReadingBuilder.KindFor(HardwareType hardwareType)`: `Cpu → CpuOther`; `GpuNvidia/GpuAmd/GpuIntel → GpuOther`; `Motherboard/SuperIO → Motherboard`; `Storage → Storage`; `Memory → Memory`; everything else → `OtherTemp`.
- New `Torrid.Core/Sensors/SensorCatalogBuilder.cs`: `static IReadOnlyList<CatalogSensor> Build(IReadOnlyList<HardwareSnapshot> hardware)` producing every temperature sensor in the tree (recursing into sub-hardware; skip sensors without an `Identifier`), as `sealed record CatalogSensor(string Id /* "hw:" + identifier */, string Name, string HardwareName, SensorKind Kind, double? ValueCelsius)`, de-duplicated by `Id`, ordered by hardware kind order (Cpu, Gpu, Motherboard, Memory, Storage, other) then hardware name then sensor name. For SuperIO sub-hardware, `HardwareName` is the parent motherboard name plus the chip name when available, otherwise the chip's own name.
- Intel/other CPU fix: the built-in `cpu` reading looks for the first Temperature sensor whose name is, in priority order: `Core (Tctl/Tdie)`, `CPU Package`, `Core Max`, `Package`, `Core Average`. `SourceSensorName` reports the one actually used. A CPU that has none still yields the `cpu` reading with `null`.

### Task 2: Footprint-minimising SensorService + Scan() (Torrid.Core)

**Files:** modify `Torrid.Core/Sensors/SensorService.cs`, `Torrid.Core/Sensors/ISensorSource.cs` (or add a new interface below), create `Torrid.Core/Sensors/HardwareGroups.cs`, `Torrid.Core/Sensors/SensorCatalogResult.cs`; modify `Torrid.App/Sensors/FakeSensorSource.cs` and the `SensorService` construction in `Torrid.App/AppHost.cs`; tests `Torrid.Tests/HardwareGroupsTests.cs`, `Torrid.Tests/SensorServicePausedTests.cs` (extend).

**Interfaces:**
- `[Flags] enum HardwareGroups { None = 0, Cpu = 1, Gpu = 2, Motherboard = 4, Memory = 8, Storage = 16 }`.
- `static class HardwareGroupsPolicy`:
  - `HardwareGroups ForLevel(HardwareAccessLevel level)` → `Paused: None`; `GpuOnly: Gpu | Storage`; `Full: Cpu | Gpu | Motherboard | Memory | Storage` (the *ceiling* — what the level permits).
  - `HardwareGroups Wanted(IEnumerable<SensorKind> addedKinds)` → always `Cpu | Gpu`, plus `Motherboard` if any `SensorKind.Motherboard`, `Memory` if any `Memory`, `Storage` if any `Storage`; `CpuOther` implies `Cpu`; `GpuOther` implies `Gpu`; `OtherTemp` implies **no** extra group (it is only found in already-open groups; it is documented as "best effort").
  - `HardwareGroups Effective(HardwareAccessLevel level, IEnumerable<SensorKind> addedKinds)` = `ForLevel(level) & Wanted(addedKinds)`. Examples in tests: Full + no added → `Cpu|Gpu`; Full + added Motherboard → `Cpu|Gpu|Motherboard`; GpuOnly + added Motherboard → `Gpu` (Storage only if wanted); GpuOnly + added Storage → `Gpu|Storage`; Paused → `None`.
- `ISensorSource` stays as is. New `interface ISensorCatalogSource { Task<SensorCatalogResult> ScanAsync(CancellationToken ct = default); }` implemented by `SensorService` and `FakeSensorSource`. `sealed record SensorCatalogResult(IReadOnlyList<CatalogSensor> Sensors, string? UnavailableReason)`; `UnavailableReason` non-null (and `Sensors` empty) when the level is Paused ("Monitoring is paused while {anti-cheat} is running.") or the scan failed ("Couldn't scan hardware: {message}").
- `SensorService` ctor gains `Func<IReadOnlyDictionary<string, AddedSensor>>? addedSensors = null` (replaced wholesale by the UI thread; the poll thread reads the reference). Each poll: compute `Effective(level, addedSensors().Values.Select(a => a.Kind))`; if it differs from the currently open group set (or level changed) → `CloseComputer()` then open a `Computer` with exactly those groups (`IsCpuEnabled`, `IsGpuEnabled`, `IsMotherboardEnabled`, `IsMemoryEnabled`, `IsStorageEnabled`); Paused / `None` opens nothing. Readings = `SensorReadingBuilder.Build(snapshots, addedIds, id => dict.GetValueOrDefault(id))`; at GpuOnly keep the existing cpu null placeholder. The fail-closed behaviours, event/lock discipline and `Dispose` semantics from Phase 4 are unchanged. The opened-group bookkeeping replaces `_openLevel` (store the open `HardwareGroups`).
- `SensorService.ScanAsync`: runs on a thread-pool thread; takes `_gate`; evaluates the current policy (the same call as `Poll`); if Paused → returns the reason without touching hardware; otherwise opens a SEPARATE temporary `Computer` with `ForLevel(level)` groups (all five at Full; Gpu|Storage at GpuOnly) — closing the live one first is NOT needed, but if the live `Computer` already has the same groups reuse it; updates it, builds `CatalogSensor`s via `SensorCatalogBuilder.Build(...)`, and always closes the temporary one in `finally`. Any exception → `UnavailableReason`.
- `FakeSensorSource` (demo): implements `ISensorCatalogSource` returning a deterministic catalog: CPU "CCD1 (Tdie)" / "CCD2 (Tdie)" / "SoC", Motherboard "VRM" / "System" / "Chipset" (hardware "ASUS ROG CROSSHAIR VIII"), Storage "Composite" ("Samsung SSD 980 PRO 1TB"), and it also produces readings for added ids found in its catalog (so the demo shows added sensors).
- `AppHost`: passes `() => ConfigManager.Config.AddedSensors` to `SensorService`; exposes the `ISensorCatalogSource` (null-safe: the real one is the `SensorService`). The Sensors page (Task 3) needs `ISensorCatalogSource`.

**Tests required (hardware-free):** `HardwareGroupsTests` (all the examples above plus `CpuOther`/`GpuOther`/`OtherTemp` implications and Paused); a `SensorService` test using a fake `IProcessLister` reporting `vgc` shows `ScanAsync` returns the Paused reason with no sensors and does not throw (hardware-safe: Paused path never opens a `Computer`); a catalog-throws-is-reported test only if it can be done without hardware (otherwise note it in the report). Demo `FakeSensorSource` tests: catalog contents; added ids produce readings.

**Behaviour:**
- Sensors page gets an **Add sensor** button (secondary style, next to Reset to defaults). It opens an inline panel (a card above the list, not a modal window) titled "Add a sensor" with: a short explanation ("Scans your hardware for temperature sensors. Scanning briefly accesses the hardware drivers (including PawnIO for motherboard and memory sensors) and is unavailable while an anti-cheat is running."), a **Scan for sensors** button (shows "Scanning…" and is disabled while running), the results grouped by hardware (hardware name as group header; each sensor row: name, current value if any, and an **Add** button, or "Added" (disabled) if already added), a **Close** button, and an empty/unavailable message from `SensorCatalogResult.UnavailableReason` or "No temperature sensors found."
